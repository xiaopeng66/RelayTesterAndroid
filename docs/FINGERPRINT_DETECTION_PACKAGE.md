## 1. 这次改了什么，为什么

三件事，分别对应用户的三条要求：

| 要求 | 做法 | 结果 |
|---|---|---|
| 检测原理跟上游保持一致 | 完整移植上游 `shared-detector-v1` 的排序器：LDA 投影 + kNN 参考距离 + 质心基线，权重、tau 校准、三条回答的聚合方式逐条照抄 | 黄金向量最差偏差 2.5e-5（排名） |
| 软件本体小一点 | 399,470 字节的参考库不再打进 APK，改为首次使用时下载 | APK 2,904,555 字节，比已发布的 1.4.0（3,201,744）**小 297,189 字节（−9.3%）** |
| 检测包做成可下载的数据包，方便更新 | 格式升到 `LMFPA002`/清单 `formatVersion: 2`（当前已是 `LMFPA003`/格式 3，见下），发布在 `bank` 预发布；新增一条命令完成"拉上游 → 构建 → 比对 → 发布"；转化交给 GitHub Actions 定时跑 | 一个 3.3 MB 的包，更新不动 APK |
| 上游更新时能收到提示 | 每次进入面板静默查一次清单，有新版就在卡片上显示「可更新到…」+「更新检测包」 | 见 §3、§9.4 |
| 库里有那些模型要看得见 | 「查看支持的模型（N 个）」打开按家族分组的模型弹窗 | 见 §3；初次实施的卡内列表记录保留于 §9.4 |

**先前实现的差异**：旧版本只做了 `0.5·z(LDA) + 0.5·z(质心)`，去掉了 kNN，并把参考库打进安装包。现在都补齐了。

**上游 2026-10-03（`d53d3f5b`）移除了它自己的核验器**：那是一个 6→1 逻辑头，只用来给出"排名与核验的第一候选是否一致"的提示，既不重排候选也不改置信度。本包因此把 verifier 从格式里删掉（`LMFPA003`），打分只剩排序器 + `softmax(tau·排序)`；旧格式（`LMFPA002`）仍可读，verifier 段按长度跳过、不参与打分。

**不要把它读成"更准了"**：见 §7 的诚实边界——完整公式与旧简化公式的差异落在噪声带内，这次改动的价值是"与上游可逐位对照 + 更新不必发版 + APK 变小"。

## 2. 检测包（格式 v3）

- 构建器：`tools/build_fingerprint_asset.py`（读上游 `data/shared_detector.json` + `data/unified_bank.json`）。
- 魔数 `LMFPA003`，清单 `formatVersion: 3`；上一个格式（`LMFPA002`/格式 2）**仍可安装、仍可打分**，App 从文件自身的魔数判断是哪种，未知格式与格式 1 的清单会被明确拒绝。
- 内容：LDA 头、质心特征库（Hellinger 355 维 + 序数块 74 维、干扰子空间、13 个环境的质心）、每模型 kNN 参考矩阵、温度 `tau`。**没有 verifier 段**（上游已移除）。
- 编码：稠密标量 int32 定点（1e-6）；kNN 参考张量（2128×429）按行 16 位量化 + 每行一个 float32 尺度。
- 当前发布：58 个模型，**2,119,616 字节**，`sha256 1d341337fdcb…`，构建于 `2026-10-03T07:40:28.536363+00:00`，上游 `data/shared_detector.json` 修订 `d53d3f5b1582`。
- **旧格式（`LMFPA002`）的 verifier 段按长度跳过**：字段顺序与旧读取器逐条一致（预处理 → 单位缩放 → 原点 → 投影基 → `mu` → `new_joint` → 逐候选 4 个高斯 → 自己的参考张量 → `active` → 逻辑头，其中逻辑头的三个向量**共用一个长度前缀**）。跳错一个字段就会与包尾错位，所以旧格式夹具保留了**完整的黄金向量对拍**，而不是只做一次解析冒烟。
- 8 位是可选档（`--ref-bits 8`，约 2.1 MB）：实测会重排约 0.05% 的近邻候选对（38/75,790），在面板的 top-8 列表里看得见，所以默认 16 位。

### 端侧解析与校验

`core/fingerprint/FingerprintBank.kt` 按上述顺序解析，并做一致性校验（两个头块 355/74 维、每模型数组长度、429 维 LDA、`basis` 行宽等于 `mu` 长度、模型 id 互不相同）。任何不一致、截断或多一个字节都会被拒绝（`FingerprintBankStore.parse` 把一切异常当成"不是检测包"）；旧格式的 verifier 段虽然不参与打分，它的每一次跳过同样走容量检查，所以截断的旧包也一样被拒。

安装通道另有三条硬约束（都有单测与隔离变异）：

- **读前先量尺寸**：超过 8 MiB 上限的已安装文件直接判超限，**不会被读进内存**（断言 `installedReads == 0`），避免一个畸形大文件把内存打满。上限判定依据的是文件长度，不是先读后判。
- **安装中断可回退**：装包采用"写主文件 → 写 `.bak`"两步。若主文件写坏或根本没写成，读取时会回退到 `.bak`；`.bak` 也读不出来才判"已安装但无法读取"。
- **删除覆盖全部可恢复文件**：先删现存回滚副本，再删主文件；任一步失败都报告失败，全部成功才清掉已安装状态。否则残留的 `.bak` 会在下次启动被重新采用，出现「删除成功后又装回去」。副本不存在时不要求额外删除，当前正在使用的仅有副本也可正常删除。

## 3. 生命周期：从"内置"到"下载一次，之后离线"

三种状态（`BankSource`）：

| 状态 | 何时 | 面板表现 |
|---|---|---|
| `NOT_PROVISIONED` | 全新安装、或用户删掉了检测包 | 未安装提示 + 「下载检测包」按钮；进入面板时会查一次清单，把下载入口摆出来 |
| `INSTALLED` | 已下载并安装 | 显示构建时间、模型数、来源；有新版时显示「可更新到…」+「更新检测包」；可打开支持模型弹窗 |
| `INSTALLED_UNREADABLE` | 已安装但读不出来 / 解析不了 | 明确文案（"无法读取"/"无法解析"，请重新下载）+ 「删除已安装的检测包」 |

- **每次进入面板都查一次清单**，所以上游一发新版，下次打开面板就看得见「可更新到…」——不用先想到去点「检查更新」。这次检查是**静默**的：只更新"有没有新版"这个状态，不弹气泡（用户没主动点，失败不该变成一条错误提示）；点「检查更新」才报告结果（已是最新 / 发现新版 / 失败原因）。
- 安装：先完整解析校验，再落盘；写入走"暂存 → 轮转 `.bak` → 原子 move"。解析不了的文件永远不会成为当前包，旧包继续用。
- 回滚：解析主文件失败时自动尝试 `.bak`，成功则面板照常用并提示"已回退到上一份"。
- 上限：8 MB（16 位全量 3.3 MB，留一倍余量给上游扩表）。
- **支持模型使用弹窗**：「检测包」卡片里的「查看支持的模型（N 个）」打开按家族分组的滚动弹窗（当前 58 个模型 / 13 个家族）。名单来自包自身，没有第二份清单；没有可读包时不显示入口。
- 检测本身**完全离线**：题目、打分、候选排序、置信度都在端侧算；联网只发生在"检查清单"和"下载包"两个动作。
- 没有推送通知：检测包更新是"打开面板时告知"，不是后台轮询，也没有系统通知。比这一版更旧的 App 只认格式 2，看到格式 3 的清单会被版本校验挡住，这时它**读不了清单的其余字段、但会先把 `minAppVersionCode` 读出来**，所以面板说的是「线上检测包需要更新版本的 App 才能使用（需要版本代码 ≥ 10505）。」而不是一个格式号；它继续用设备上已装的那份包，不受影响，升级 App 后再点「检查更新」即可装上。

### 打分口径

- 三条有效回答 → 完整路径：`ranking = 0.5·z(mean(LDA投影)) + 0.25·z(median(−kNN距离)) + 0.25·z(mean(质心基线))`，置信度是 `softmax(tau·ranking)`。
- 1–2 条有效回答 → 部分路径（`shared-ranker-partial-v1` 等价语义）：只出候选排序，明确不给置信度，面板文案写清"补齐三条才有置信度"。
- 有效回答门槛沿用上游：`max(80, ceil(expected_count × 0.55))`。
- **有意偏离上游的一处**：上游用四个哈希把 `tau` 绑到它拟合时的制品上；我们的包就是那个绑定的产物，所以这一层退化成"包能解析且 `tau` 在 [0.001, 1000] 内"。已在 `SharedScoring.kt` 的文件头注明。

## 4. 上游对齐是怎么被证明的

`app/src/test/java/com/relaytester/app/FingerprintGoldenTest.kt` + `FingerprintLegacyPackageTest.kt` + `app/src/test/resources/fingerprint-golden.json`（以及 `-legacy` 那一份）：

- 黄金向量由**上游自己的** `shared/shared-detector.ts`（`analyzeSharedOutputs`）跑出来的 8 组用例（6 个模型的真实回答 + 一条部分样本用例），不是第二份实现；生成器会拒绝"包的构建时间与检测器不一致"的组合（那会让上游静默退回旧排序器）。六个模型跨 6 个家族（GPT / Claude / Gemini / Grok / GLM / DeepSeek），家族汇总判定才有意义。
- 断言：候选顺序、首位候选、家族、逐模型排名分与置信度（容差 1e-4）、评分路径、置信度状态、截断包被拒。
- **旧格式（`LMFPA002`）用自己的夹具与黄金向量跑同一套断言**：verifier 段是跳过去的，只有排名与置信度都对上，才能证明"跳过"没有错位。这条测试在开发中真的抓到过一次错位——逻辑头的三个向量共用**一个**长度前缀，按三个前缀去跳就会整体偏移。
- 实测最差偏差（量化的代价）：排名 2.5e-5、置信度 1.2e-5；8 组用例的完整顺序 8/8 一致，120 个候选对 0 反序。
- 隔离变异：改掉排序器的任一处（例如把 kNN 项的权重改成别的值）→ `FingerprintGoldenTest` **变红**；旧格式那一份同理，跳段少读一个字段也必红。

### 夹具与黄金向量是"钉住"的

`app/src/test/resources/lm-fingerprint/lite-bank-small.bin`（格式 3、6 模型、228,260 字节）+ 对应的黄金向量，以及 `lite-bank-legacy.bin`（格式 2、同一批 6 模型、421,112 字节）+ `fingerprint-golden-legacy.json`，各自对应某个**固定的上游修订**，故意不随上游漂移：测试向量必须是不变的，否则"上游变了"和"我们改坏了"分不开。要重新钉一份修订时的步骤（`--pick` 用跨家族的几个模型，保住家族汇总的覆盖面）：

## 5. 更新一个检测包（运维）

**平时不用管：上游一变，GitHub Actions 自己重建并发布。** 工作流
`.github/workflows/update-detection-package.yml` 每天 03:17 UTC 跑一次，也可以在
Actions 页面点 "Run workflow" 手动跑（可选 `force` 用来验证发布通道）。它做的事：

1. `git ls-remote` 取上游 `Ikaleio/lm-detector` 的 HEAD（不用 API、不限流）；
2. clone 本仓库（默认分支）→ 下载上游那一个修订的 `data/*.json`（44 MB）；
3. `python tools/update_fingerprint_package.py --revision <上游 HEAD>`：重建 → 读**重建文件自己的魔数**决定清单的 `formatVersion`（`LMFPA003` ⇒ 3、`LMFPA002` ⇒ 2，不再是写死的常量）→ 与线上清单比 `sha256` → **一致就打印"无需发布"**；
4. 发布时把两个资产**下载回来逐字节比对**，对不上就让 job 失败。

同一条命令本机也能跑：

```bash
python tools/update_fingerprint_package.py            # 检查上游 → 按需重建 → 与线上比对 → 变了才发布
python tools/update_fingerprint_package.py --dry-run  # 全流程但不发布
python tools/update_fingerprint_package.py --revision <sha>   # 跳过 API，直接用这个上游修订
python tools/update_fingerprint_package.py --refresh  # 忽略缓存，重新下载上游数据（44 MB）
python tools/update_fingerprint_package.py --data-dir /path/to/lm-detector/data   # 用本地上游副本
python tools/publish_bank.py --check                  # 只校验线上资产与本地是否逐字节一致
```

- **幂等来自构建的确定性**：包头的 `builtAt` 取自上游数据里的字段，不是时钟；同一份上游数据重建出的字节完全相同（实测重建得到的 `sha256` 与线上发布的一模一样）。所以"上游没动"的日子，这一步只是重算一遍再比一下。
- 判定依据是上游那个修订（CI 里就是上游 HEAD）。**上游因为无关文件挪动 HEAD 时也会重建一次**，重建结果与线上一致，同样"无需发布"——代价是一次 44 MB 下载，不会误发。
- 产物：`build/lm-fingerprint/lite-bank.bin` + 从文件头反读出来的 `latest.json`（构建时间、模型数、参考摘要、大小、SHA-256、`minAppVersionCode`），两者不可能互相漂移。
- 发布后会把两个资产**下载回来逐字节比对**；刚替换的资产可能被 CDN 缓存一瞬，所以回读带 cache-buster 并重试 5 次（这是实测踩到的假失败：内容其实已经正确）。
- 失败模式：GitHub API 限流 → 提示写 token（CI 里不走 API，所以只影响本机）；`raw.githubusercontent.com` 不可达 → 设置 `HTTPS_PROXY` 或用 `--data-dir`（CI 跑在 GitHub 自己的网络上，实测正常）。
- Token：本机是 `GITHUB_TOKEN` 或 `E:/AI/Zcode/tmp/.ghtoken` 第一行；**CI 用的是本次运行自己的临时 `GITHUB_TOKEN`，仓库里没有配任何 secret**。

### 5.2 瞬时失败怎么自愈（两层重试，2026-10-04）

没有人守在 03:17 的运行旁边，所以"一次瞬时抖动 = 一整天的红 run"这件事被拆成两层处理。判据只有一条：**这个答案是不是"稍后就好"**——是就重试，不是就立刻带着原话失败。

| 层 | 覆盖什么 | 上限与证据 |
|---|---|---|
| ① 步骤内（`tools/retry.py`） | GitHub API（发布/删除资产/上传/回读）、`raw.githubusercontent.com` 的 44 MB 下载、上游 API；`git ls-remote` 与 `git clone` 由工作流自己 loop 三次 | 默认 4 次，退避 2s→4s→8s 封顶 30s，带轻微抖动；服务端给了 `Retry-After` 就按它等（上限 120s）。`BANK_RETRY_ATTEMPTS/_BASE_DELAY/_MAX_DELAY/_JITTER` 可按运行覆盖 |
| ② 运行级（`tools/retry_failed_runs.py` + `.github/workflows/retry-failed-detection-package.yml`） | 步骤内够不到的情况：runner 杀掉 job、步骤超时、`git clone` 起不来、没预料到的异常、GitHub 侧在运行中途故障 | 同一个 run 最多跑到 attempt 3（可调），只认 24 小时窗口内的失败，`workflow_run` 触发让重跑在几分钟内发生（另有每小时 `schedule` 兜底） |

哪些**不**重试：`401/404/422/409`（请求本身就是错的，重复一万次也一样）、`cancelled`（有人主动取消）、`startup_failure`（工作流文件本身被拒，重跑不可能成功）、`action_required`（在等人审批）。403 单独判：响应头说额度用尽（`X-RateLimit-Remaining: 0` 或带 `Retry-After`）才算瞬时，否则是 token 没权限，立刻失败。

**两层都不会动发布本身**：②只调用 `rerun-failed-jobs` 让 GitHub 把同一个 run 的失败任务重跑一遍（它只申请 `actions: write`，没有 `contents: write`，碰不到 release 和资产）；而发布是幂等的——重建是确定性的、上传前比 `sha256`、上传后逐字节回读，所以重跑要么打印"无需发布"，要么把缺的资产补上，**不可能发两份，也不可能发出旧包**。发布工作流自己的 `concurrency`（`cancel-in-progress: false`）还保证重跑只会排队，不会与下一次发布并行。

**留下真实失败不掩盖**：一直失败的 run 在跑满 attempt 上限后就留在红色——那是真问题，无限重试只会把它藏起来。`retry_failed_runs.py --dry-run` 可以在本机只读地看"它现在会重跑哪些"（对着真实 API 跑过：8 次历史运行里挑出 0 个——两次历史失败都已被后来的成功运行覆盖，所以按"已有更新的成功运行"规则跳过）。

### 5.3 应用自身更新的清单（`app` 预发布，2026-10-04）

检测包是**数据**的更新源，1.6.0 起 App 自己也有一个（`app` 预发布里的 `app-latest.json`）。两者是同一支脚本发出的两个资产、两个发行版，**互不碰对方的资产**，所以检测包的每日自动重建不可能误删 App 的更新清单。

```bash
python tools/publish_release_apk.py --dry-run   # 打印 APK 信息与将要发布的清单，不联网
python tools/publish_release_apk.py             # 传 APK + 发行说明（v<版本>），再传/更新清单（app）
python tools/publish_release_apk.py --check     # 只回读校验：APK 逐字节、清单逐字节 + 逐字段
```

- **清单从产物本身推导**：包名、版本代码、minSdk 用 `aapt2 dump badging` 从 APK 里读；体积与 SHA-256 取同一份字节。因此清单不可能描述另一份构建，也不受 `defaultConfig` 里的包名影响（变体的 `applicationIdSuffix` 会进 APK，App 比对的是它自己安装时的包名）。
- **版本代码是唯一可靠的比较信号**：本仓库沿用同一个版本名重新发布（10500 → 10505 版本名都是 1.5.0），`api.github.com/repos/.../releases/latest` 又只能给 tag，拿 tag 或版本名比较会把还在 10502 的安装判成"已是最新"。这也是不用 GitHub API 的原因之一（另一个原因是匿名 60 次/小时的限额）。
- **上传顺序是先 APK 后清单**：清单永远不会为一个还不存在的安装包做广告。上传后两个资产都回读逐字节比对；清单还逐字段核对（包名 / 版本代码 / 版本名 / 体积 / 摘要 / 地址），所以"发了一版陈旧清单"在脚本里就止住。
- **复用检测包那条发布链**：`publish_bank.py` 的 `release_by_tag` / `ensure_release` / `replace_asset` 把 tag 与 release 名参数化（默认值不变，所以检测包路径零改动），回读走 `retry.py` 的瞬时重试。
- **只在本机手动跑**：仓库里没有 APK 的 CI（只有检测包的工作流）。"发了新 APK 却忘了发清单"由这一条命令兜住——它一次做两件事，并在最后打印版本代码。
- `apkUrl` 指向 `v<版本>` 发行版里那个资产（`https://github.com/<repo>/releases/download/<tag>/RelayTester-<tag>-android.apk`），字面量与 `replace_asset` 上传时用的名字同源，不是从 API 响应里抄的。

### 5.1 这套自动化的安全边界

| 问题 | 实际情况 |
|---|---|
| 别人装了 App，能不能碰我的 GitHub？ | 不能。APK 里**没有任何凭据**，它只会对公开的 `releases/download/bank/latest.json` 做匿名 GET；应用代码里全仓只有这一个 GitHub URL（`BankUpdate.kt`）。装 App 的人最多产生下载流量。 |
| CI 用的是什么凭据？ | 运行自带的 `GITHUB_TOKEN`：本仓库作用域、跑完即失效。**发布工作流**只声明它需要的 `contents: write` + `issues: write`（仓库默认权限本身是只读的）；**重跑工作流**只声明 `actions: write`——它需要这个权限来调 `rerun-failed-jobs`，但拿不到 `contents: write`，所以碰不到 release、资产或仓库文件。两处都**没有 PAT、没有仓库 secret**，没有可被偷的长期凭据。 |
| 谁能触发这个工作流？ | 只有 `schedule` 和 `workflow_dispatch` 两种触发，**没有 `push`/`pull_request`**，所以通过 fork 或 PR 送进来的代码永远不会在这个 job 里跑；`workflow_dispatch` 也只有写权限的人能点。重跑工作流由 `workflow_run`（发布工作流结束）+ `schedule` + `workflow_dispatch` 触发，同样没有 `push`/`pull_request`；它只重跑**本仓库已有**的运行，不能凭空发起一次发布。 |
| 自动重跑会不会把发布搞坏？ | 不会，见 §5.2：重跑的是同一个 run 的失败任务（同 commit、同输入），发布幂等（确定性重建 + 摘要比对 + 回读），且没有 `contents: write`。它唯一能做的写操作是"让 GitHub 再跑一次那几个任务"。 |
| 第三方 action 会不会被投毒？ | 用不到第三方 action：整个工作流只有 `git`、`python3` 和 runner 自带工具（因此也**没有可被移动 tag 劫持的依赖**）。 |
| 仓库要不要保持公开？ | 要。App 不带凭据 ⇒ 资产必须匿名可读。把仓库转私有会让更新功能整体失效（这是设计前提，不是疏漏）。 |
| 上游数据本身有毒怎么办？ | 上游是第三方仓库，这是唯一的供应链面。缓解：构建脚本是我们自己的、只把数值打包；App 侧安装前先解析校验（格式/边界/大小），解析不过就拒绝安装并保留原包。**没做到的**：CI 里没有跑 Kotlin 黄金向量（缺 Android 工具链），所以"数值正确性"这一层仍靠本机 `:app:testOptimizedUnitTest` 把关。 |
| 定时任务会不会自己停？ | 会。公开仓库 60 天没有仓库活动时，GitHub 会自动停掉定时工作流并给仓库所有者发邮件。停了不影响任何人使用（线上包保持现状），Actions 页面点一下 Enable 再用 "Run workflow" 跑一次即可。 |

## 7. 诚实边界

1. **不宣称准确率提升。** 准确率评估（`FINGERPRINT_ACCURACY_OPTIMIZATION_SPEC.md` §1.2）：无泄漏口径下完整公式逐模型 48/53、逐回答 372/491，旧简化公式 47/53、386/491——两个方向的差都在 ±5 点的噪声带内。注意这组分母 **53** 是当时评估用的包；本轮包随上游扩到 **58** 个模型，没有重跑准确率评估，所以不把这组数字移植到新包上（沿用它们会把两个包的样本混为一谈）。这一轮的目标仍是"对齐上游 + 可更新 + 更小"，不是"更准"。
2. **kNN 的体积换来的不是精度**：16 位参考张量让包从 0.4 MB 涨到 3.3 MB，收益是可逐位对照上游；8 位能让包回到 2.1 MB，代价是 0.05% 的近邻候选对被重排。
3. **余量：0.05% 是量化尺度上的近似说法**。1e-4 的断言容差是"实测最差 2.5e-5"的 4 倍；包再被裁一次（模型数变化）需要重新测量。
4. **"库外模型判定"没有做**。面板只给库内最接近的候选与置信度，不输出"这个回答不像库内任何模型"。前提缺失：本地没有库外模型的回答样本，假接受率无法测量（同上文 §6.2）。
5. **旧版 App 无法使用新包**：格式版本门是硬的（只认格式 2 的 App 读不了格式 3 的清单）。它继续用设备上已装的那份包（或者它内置的那一份）。面板会明确说「线上检测包需要更新版本的 App 才能使用（需要版本代码 ≥ N）」——`minAppVersionCode` 在格式判定之前读取，正是为了这条提示可执行（`BankFormatTooNewException`）；升级 App 后再点「检查更新」即可装上。**已经装在设备上的旧版 App 改不了**：它里面的代码没有这一段，只能手动装一次新包。
6. **设备 E2E 的覆盖与缺口**：已在模拟器上走通"未安装空态与自动查清单 → 真实下载安装（落地文件 sha256 与线上一致）→ 已是最新 → 坏包回退 → 无备份时判不可读 → 删除回未安装"，用手动粘贴跑通一次**真实打分**（见 §9），并在真机式走查里展开过模型列表（见 §9.4）。**没做**的：多模型批量检测的设备走查、设备上走"更新检测包"（覆盖安装）这一条、飞行模式下的离线文案、真机（非模拟器）。
7. **模型列表本身没有自动化 UI 测试**：项目里没有 compose-ui-test / Robolectric，`查看支持的模型` 只有两层证据——状态层（单测断言 `bankModels` 与包内名单逐项一致）与设备层（§9.4 的展开/滚动/首末条）。列表的渲染循环、折叠状态、滚动表现靠设备走查，不靠单测；改这部分要重新走一遍设备。
8. **CI 只守通道，不守数值**：工作流能保证"上游变了就重建、变了才发、发完回读一致"，但它**不跑 Kotlin 黄金向量**（runner 上没有 Android 工具链）。也就是说"发出去的包数值是否正确"仍靠本机 `:app:testOptimizedUnitTest` + 夹具黄金向量把关；CI 抓不到"能解析但数值错"的包。App 侧还有一道兜底：装之前先解析校验，解析不过就拒绝安装并保留原包。
9. **定时任务会自己停**：公开仓库 60 天无仓库活动，GitHub 会停掉 `schedule`（并发邮件）。这不是故障，线上包保持现状、App 照常工作；Actions 页面 Enable + "Run workflow" 即可恢复。见 §5.1。
10. **发布有一个很短的"资产不在"窗口，失败会自愈**：更新时先删旧资产再传新资产（GitHub 不允许同名资产并存），两次请求之间 `bank` 预发布短暂没有任何资产。若工作流正好死在这中间，线上包会空缺；下一次运行（以及 §5.2 的自动重跑）会重建并重新发布（内容不变时产物逐字节一致，重发是幂等的）。**发布后的回读校验是可重试的**：刚上传的资产还在 CDN 传播时读取可能拿到 `503`，`publish_bank.verify` 把它与"字节不一致"同等对待（6 次 × 5 秒），只有连续失败才判红——2026-10-03 第一次重发就死在"回读拿到 503"上，那一步是瞬时错误而不是发布失败，修好后重发 6 个步骤全绿。**上传永久失败时消息会明说"release 里现在缺少哪个资产"**（否则一次 401 会只留下一个看不出后果的报错）。
11. **`app` 更新清单的线上路径从未真正跑过**（2026-10-04）：新代码的门禁覆盖了"清单从产物推导"（`--dry-run` 对着真实 APK 跑通，字段逐项核对）与"清单回读校验"的判据（本地起 HTTP 服务喂好/坏清单），设备走查（§8.6）用的也是本地清单宿主、不是 GitHub；但 `ensure_release` 创建 `app` 预发布这一步只在检测包的 CI 上被验证过同一段代码。**首次发布时会一并暴露**：清单要么按预期出现并回读一致，要么发布脚本在创建/上传那一步带着 HTTP 状态失败，两种情况都不会留下"半个发布"（APK 与清单都是先上传后回读，清单在最后）。
12. **App 自身更新面的设备走查与签名方式（2026-10-04）**：清单解析、版本比较、节流、开关落盘、下载校验、安装权限分支都有单测与变异红证，**设备上真的点一遍也做了**——入口图标与角标、更新页的四种状态、下载字节进度递增、「去更新软件」的跳转、权限页 → 系统安装器的交接，连检测包从清单下载安装一起，**一次串联 42/42**（见 §8.6）。走查的清单由本地宿主提供（两个 feed 的线上地址都还不存在）：两个源文件改回来后按 SHA-256 逐字节核对，重建的产物里 0 处 mock 地址。签名与包名**已切到正式发布密钥**（包名 `com.relaytester.app`，证书 `CN=Relay Tester`，v2 + v3 签名，口令在仓库外的 `gradle.properties` 里，见 `RELEASE_SIGNING.md`）：切完后重新装到模拟器上确认能装能跑、更新页读回 `当前版本 1.6.0（版本代码 10600）`。代价是**旧包（`com.relaytester.app.debug`，调试签名）与新包是两个不同的应用**，老用户要"导出配置 → 卸载 → 装新包 → 导入配置"一次；这是唯一一次——之前的密钥在换机器时会丢失、导致所有人被迫重装，正式密钥把这条路封住了。真机（不同厂商的安装器 UI 与「未知来源」入口位置都不一样）不在本轮范围内。

**一条存活过的变异（记在此处，因为它是判据本身的教训）**：把"格式版本号超出上限"的边界改成差一（`>` 改 `>=`）最初**没被抓住**——受影响的测试里 `minAppVersionCode` 设得比已装版本高，于是客户端自己的版本门先命中了，两条代码路径给出同一个对象，测试钉住的是那个门而不是格式分支。把测试的 `minAppVersionCode` 改成低于已装版本（`10_500` < 已装 `10_505`）之后，格式分支才成为唯一出口，变异立刻变红。

**第二类假"存活"来自门禁自己读错了源码（2026-10-04 抓到）**：`app_manifest_gate.py` 用 `importlib` 加载发布脚本，而 CPython 的字节码缓存只按 **`(int(mtime), size)`** 判新旧。变异电池在同一秒内连续写入，其中两条恰好都让文件**长了 4 字节**（`{tag}`→`{APP_TAG}` 与常量包名替换），于是第二条变异被判在**第一条的编译结果**上——门禁报出的失败属于上一条变异，"包名变异存活"是假象。判据是**孤立复现**：单独注入那一条变异、直接跑门禁，期望的检查立刻变红（35/37）。修法=门禁不再经过缓存，`exec(compile(source, path, "exec"))` 编译刚读到的字节，并加一条断言（门禁执行的模块必须就是磁盘上这一份，加回 `importlib` 即变红）。**教训：变异电池"存活"必须先孤立复现，再判是被测代码等价还是工具链在骗人**；顺带记一笔，`tools/__pycache__/` 里的旧 `.pyc` 就是这么把一次真实存在的红证变成了假绿。

### 9.3 环境坑（下次少走弯路）

- **GitHub release 资产的 CDN 在模拟器里直连不通**：同一时刻小的 JSON 请求正常，`release-assets` 的 TLS 握手 45 s 超时。宿主上用 `ProxyHandler({})` 复现同一现象 ⇒ 是网络环境，不是应用缺陷。给模拟器挂宿主 Clash（`10.0.2.2:7897`，allow-lan 已开）后下载正常。
- **模拟器全局代理要重启才生效**：`settings put global http_proxy…` 写完当次不生效，`am broadcast android.intent.action.PROXY_CHANGE` 是 root-only（Permission Denial）。必须 `adb reboot`。验证时别只看应用日志——失败原因只在界面 snackbar 上（OkHttp 走 `onFailure` 包装），截图才看得到 `Failed to connect to /127.0.0.1:7897`。
- **`adb push` 的设备路径在 Git Bash 里会被改写**：`adb push x /data/local/tmp/y` 报成功但文件不在。写 `//data/local/tmp/y`。
- **`run-as` 不能直接 `cp`**：应用 uid 进不去 `/data/local/tmp`；用设备侧管道 `cat src | run-as <pkg> sh -c "cat > target"`。
- **Compose 手输长文本**：输入框在被键盘遮住时不会出现在 uiautomator 树里（未组合），得先 `input keyevent 4` 收起键盘（IME 会吃掉这次返回，面板不受影响）再滚动；`input text` 按 ~260 字符分段注入，整段 800 字符会被静默截断。
- **别用路径认产物**：`tmp/fp_v2/lite-bank.bin` 与线上发布的包**同名不同内容**（`30a86314…` vs `4bdd1d3b…`），拿它复算会得到另一套候选顺序。对账一律先比 sha256。
- **`adb shell … > file` 会把二进制拉坏**：Git Bash 的 shell 形态带 pty，换行被翻译成 CRLF，3,476,998 B 的文件落地成 3,509,317 B（多出的正是行数），sha256 也就跟着变。取二进制必须 `adb exec-out run-as <pkg> cat <file> > out`。
